# Чек-лист разбора медленного запроса

## Индексы

- [ ] Есть ли индекс по колонкам из `WHERE` в правильном порядке (сначала равенство, потом диапазон)?
- [ ] Покрывающий индекс (`INCLUDE`) избавит от обращения к куче?
- [ ] Частичный индекс (`WHERE deleted_at IS NULL`) не сократит ли размер в разы?
- [ ] Не мешает ли функция над колонкой (`WHERE lower(email) = ...`) использовать индекс?
- [ ] Совпадает ли тип параметра с типом колонки — иначе индекс не применится?

## Статистика

- [ ] Когда последний раз проходил `ANALYZE` по таблице (`pg_stat_user_tables.last_analyze`)?
- [ ] Не нужна ли расширенная статистика (`CREATE STATISTICS`) для коррелированных колонок?
- [ ] Не задран ли `default_statistics_target` слишком низко для перекошенных данных?

## Форма запроса

- [ ] `OR` по разным колонкам не мешает ли использовать индексы — не разложить ли на `UNION ALL`?
- [ ] `NOT IN` с подзапросом не переписать ли на `NOT EXISTS` (иначе NULL ломает семантику и план)?
- [ ] `OFFSET` на большой странице — не заменить ли на keyset-пагинацию по `(created_at, id)`?
- [ ] `DISTINCT` не прикрывает ли лишний join, размножающий строки?
- [ ] `COUNT(*)` по всей таблице — точное число вообще нужно или хватит оценки из `pg_class.reltuples`?

## Блокировки и конкуренция

- [ ] Запрос точно медленный сам по себе, а не ждёт блокировку (`pg_stat_activity.wait_event`)?
- [ ] Не попадает ли он в долгую транзакцию, которая держит снапшот?

## Замеры

- [ ] Есть ли `EXPLAIN (ANALYZE, BUFFERS)` до и после изменения?
- [ ] Прогрев кеша учтён — сравниваем второй прогон со вторым, а не первый со вторым?
